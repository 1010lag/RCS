# Push на телефоне

## Подключение Firebase

Firebase-проект — настройки внешнего сервиса уведомлений, а не новый GitHub-репозиторий. Можно использовать уже существующий Firebase-проект. Новый нужен только при отсутствии подходящего проекта.

При доступном официальном подключении Firebase нужно войти в Google-аккаунт с доступом к выбранному проекту. Не передавайте закрытые ключи в чат или в клиентскую сборку.

Для локальной конфигурации предусмотрена команда:

```sh
npm run push:setup
```

Она запрашивает публичный JSON Web-конфигурации Firebase, публичный VAPID-ключ, путь к JSON сервисного аккаунта **вне репозитория** и адрес приложения. Проверяет структуру, ключ и соответствие Firebase-проекта серверному аккаунту, затем обновляет исключённый из Git `.env`. После этого нужно перезапустить API. Проверка файла не подтверждает доступ к облачному API: фактическую авторизацию проверит отправка тестового push.

Вместо файла ключа в окружениях Google с прикреплённым сервисным аккаунтом можно использовать `FIREBASE_USE_ADC=1` и Application Default Credentials. Локальная команда настройки использует путь к файлу. Серверному аккаунту нужны права отправки FCM; должен быть включён Firebase Cloud Messaging API. [Firebase Admin SDK](https://firebase.google.com/docs/admin/setup), [отправка сообщений](https://firebase.google.com/docs/cloud-messaging/send/admin-sdk).

Web-конфигурация находится в настройках зарегистрированного Web-приложения Firebase. Публичный VAPID-ключ создаётся в Cloud Messaging → Web Push certificates. Используйте настройки одного Firebase-проекта. [Официальная настройка Web Push](https://firebase.google.com/docs/cloud-messaging/web/get-started).

## Адрес приложения

На телефоне нужен доступный HTTPS-адрес работающего RCS с API. `localhost` на телефоне означает сам телефон, а не компьютер с этим проектом. Локальная проверка на компьютере разрешает `http://localhost`; это не подключение телефона.

Публикация интерфейса без работающего API и worker не обеспечивает уведомления о сменах. Конфигурация сама по себе также не создаёт хостинг.

## Подключение устройства

1. Открыть RCS на телефоне и войти под своим аккаунтом.
2. На iPhone/iPad добавить приложение на экран «Домой» и открыть с иконки. Это условие Web Push для iOS/iPadOS. [WebKit: Web Push](https://webkit.org/blog/13878/).
3. В «Профиль» нажать «Включить push на устройстве» и разрешить уведомления.
4. Нажать «Проверить push». Кнопка отправляет сообщение только на текущее устройство этого пользователя.
5. Проверить системное уведомление, затем нажатие на него. Принятие сообщения Firebase не означает подтверждённую доставку устройством.

Сервер показывает диагностику конфигурации только админу, не раскрывает закрытый ключ или путь к нему. Бариста видит состояние своей подписки. Отключение устройства не удаляет подписки с других телефонов.

## Доставка и проверки

Уведомления хранятся на сервере. Worker отправляет их через Firebase, повторяет временные ошибки с задержкой, удаляет устаревшие токены и проверяет настройки категорий. Старое уведомление не отправляется другому аккаунту после переназначения токена. Устаревшие напоминания не уходят после смены владельца или версии смены.

Service worker сам показывает data-only сообщения, используя идентификатор уведомления как tag. Это позволяет избежать двух уведомлений от одновременного автоматического и ручного показа. Внешние адреса в ссылках уведомления отбрасываются. [FCM: обработка сообщений](https://firebase.google.com/docs/cloud-messaging/web/receive-messages).

Автоматические проверки заменяют Firebase тестовым отправителем: проверяют маршруты, очередь, повторные попытки, приватность, сообщения service worker и кнопки интерфейса. Они не доказывают реальную доставку на телефон. Проверка выбранного Firebase-проекта и настоящего устройства выполняется после подключения аккаунта и HTTPS-адреса.
