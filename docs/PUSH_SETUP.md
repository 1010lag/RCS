# Push на телефоне

## Устанавливаемое Android-приложение

Для APK нужны Firebase-проект, зарегистрированное Android-приложение с пакетом `by.rcs.app`, его `google-services.json` и серверные credentials с правом отправки FCM. Web-приложение, VAPID и HTTPS-хостинг для нативных push не требуются. Для работы с локальным API телефон использует домашнюю сеть, а уведомления получает от Firebase. Компьютер с API/worker должен работать, чтобы создавать и отправлять события.

1. В Firebase Console выбрать проект → Add app → Android. Указать `by.rcs.app`, скачать `google-services.json` в `android/app/`. Для FCM SHA-1 необязателен.
2. В Project settings → Service accounts создать серверный ключ; сохранить **вне репозитория**. Для отдельного отправителя достаточно роли `roles/firebasecloudmessaging.admin`; включить Firebase Cloud Messaging API.
3. Выполнить `npm run push:setup -- --android` и указать путь к ключу. Скрипт определяет Firebase project ID и записывает его с путём credentials в исключённый из Git `.env`.
4. Перезапустить API, выполнить `npm run android:build` и установить новый APK. Сборка проверяет пакет Android-приложения, включает регистрацию FCM и запоминает project ID для проверки соответствия серверу.
5. В профиле телефона нажать «Включить уведомления Android» и разрешить уведомления. Кнопкой «Проверить push» проверить принятие сообщения Firebase, затем его фактическое появление в системных уведомлениях. Отдельно проверить доставку, когда RCS находится в фоне, и открытие сообщения.

Канал `rcs` создаётся нативным приложением при запуске. Иконка и канал по умолчанию определены в AndroidManifest; сообщения в фоне отображает FCM, в открытом приложении — нативный модуль с presentationOptions. Сохранённая одобренная подписка обновляется при возвращении в приложение; разрешение повторно не запрашивается автоматически. При регистрации передаётся ожидаемый пользователь, чтобы поздний ответ Firebase не привязал телефон к другому аккаунту.

[Официальная настройка Android](https://firebase.google.com/docs/cloud-messaging/android/get-started), [Capacitor Push](https://capacitorjs.com/docs/apis/push-notifications).

## Браузер и PWA

Firebase-проект — настройки внешнего сервиса уведомлений, а не новый GitHub-репозиторий. Можно использовать уже существующий Firebase-проект. Новый нужен только при отсутствии подходящего проекта.

При доступном официальном подключении Firebase нужно войти в Google-аккаунт с доступом к выбранному проекту. Не передавайте закрытые ключи в чат или в клиентскую сборку.

Для локальной конфигурации предусмотрена команда:

```sh
npm run push:setup
```

Она запрашивает публичный JSON Web-конфигурации Firebase, публичный VAPID-ключ, путь к JSON сервисного аккаунта **вне репозитория** и адрес приложения. Проверяет структуру, ключ и соответствие Firebase-проекта серверному аккаунту, затем обновляет исключённый из Git `.env`. После этого нужно перезапустить API. Проверка файла не подтверждает доступ к облачному API: фактическую авторизацию проверит отправка тестового push.

Вместо файла ключа в окружениях Google с прикреплённым сервисным аккаунтом можно использовать `FIREBASE_USE_ADC=1` и Application Default Credentials. Локальная команда настройки использует путь к файлу. Серверному аккаунту нужны права отправки FCM; должен быть включён Firebase Cloud Messaging API. [Firebase Admin SDK](https://firebase.google.com/docs/admin/setup), [отправка сообщений](https://firebase.google.com/docs/cloud-messaging/send/admin-sdk).

Web-конфигурация находится в настройках зарегистрированного Web-приложения Firebase. Публичный VAPID-ключ создаётся в Cloud Messaging → Web Push certificates. Используйте настройки одного Firebase-проекта. [Официальная настройка Web Push](https://firebase.google.com/docs/cloud-messaging/web/get-started).

## Адрес приложения

Для браузера/PWA на телефоне нужен доступный HTTPS-адрес работающего RCS с API. `localhost` на телефоне означает сам телефон, а не компьютер с этим проектом. Локальная проверка на компьютере разрешает `http://localhost`; это не подключение телефона. Нативный APK проверяется отдельно и поддерживает локальный API.

Публикация интерфейса без работающего API и worker не обеспечивает уведомления о сменах. Конфигурация сама по себе также не создаёт хостинг.

## Подключение устройства

1. Открыть RCS на телефоне и войти под своим аккаунтом.
2. На iPhone/iPad добавить приложение на экран «Домой» и открыть с иконки. Это условие Web Push для iOS/iPadOS. [WebKit: Web Push](https://webkit.org/blog/13878/).
3. В «Профиль» нажать «Включить push на устройстве» и разрешить уведомления.
4. Нажать «Проверить push». Кнопка отправляет сообщение только на текущее устройство этого пользователя.
5. Проверить системное уведомление, затем нажатие на него. Принятие сообщения Firebase не означает подтверждённую доставку устройством.

Сервер показывает диагностику конфигурации только админу, не раскрывает закрытый ключ или путь к нему. Бариста видит состояние своей подписки. Отключение устройства не удаляет подписки с других телефонов.

## Доставка и проверки

Уведомления хранятся на сервере. Worker отправляет их через Firebase, повторяет временные ошибки с задержкой, удаляет устаревшие токены и проверяет настройки категорий. Старое уведомление не отправляется другому аккаунту после переназначения токена. Устаревшие напоминания не уходят после смены владельца или версии смены.

Каждое push-устройство привязано к действующей сессии. Выход, её истечение, удаление сотрудника и смена пароля отзывают соответствующие подписки и очередь доставки. При смене пароля отзываются все старые сессии, включая копии текущей; клиент получает новый cookie и CSRF и может включить push заново. Старые устройства без привязки к сессии отключаются при обновлении схемы.

Service worker сам показывает data-only сообщения, используя идентификатор уведомления как tag. Это позволяет избежать двух уведомлений от одновременного автоматического и ручного показа. Внешние адреса в ссылках уведомления отбрасываются. [FCM: обработка сообщений](https://firebase.google.com/docs/cloud-messaging/web/receive-messages).

Автоматические проверки заменяют Firebase тестовым отправителем: проверяют маршруты, очередь, повторные попытки, приватность, сообщения service worker и кнопки интерфейса. Они не доказывают реальную доставку на телефон. Отдельно 1 ноября 2026 года Firebase `rcs-pro` доставил системные уведомления на Redmi 15 в открытом приложении и в фоне через серверный worker; текст с датой проверен как `02.11.2026`. Android использовал локальный API в домашней сети. Web Push и iPhone требуют отдельной настройки и проверки.

## Служебные события

Изменения команды и типов смен сохраняются только в журнале. «Команда обновлена», «Типы смен обновлены» и «Новый сотрудник» не создают новые уведомления, скрыты из списка старых уведомлений и не отправляются из старой очереди. Личные изменения ставки и начислений, события графика, биржа, напоминания и вручную отправленные сообщения управляющего продолжают работать по настройкам получателя.
