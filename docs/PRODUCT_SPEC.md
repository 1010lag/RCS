# RCS — спецификация продукта и MVP

Дата: 01.11.2026. Основание: [исходное задание](ORIGINAL_REQUIREMENTS.txt).
Статус: проектное решение для реализации, а не описание уже работающей системы.

## 1. Продукт

RCS помогает команде одной кофейни видеть график, передавать смены и понимать свои часы и начисления. Бариста пользуется мобильным PWA, администратор — адаптивной веб-панелью. Обе части работают с единым сервером и PostgreSQL.

Основной результат для бариста: за несколько секунд увидеть следующую смену, её длительность и ожидаемую оплату. Для администратора: составить график, найти незакрытые назначения и управлять командой без разрозненных таблиц и переписки.

Границы: одна кофейня, русский язык, BYN, неделя с понедельника, даты ДД.ММ.ГГГГ, время ЧЧ:ММ, часовой пояс Europe/Minsk. Мультифилиальность, ночные смены, вычитание обеда и официальный кадровый/бухгалтерский документооборот в продукт не входят. Расчёты информационные.

## 2. Роли и права

| Действие | Бариста | Админ |
| --- | --- | --- |
| Общий график: дата, время, тип, имя, статус | Да | Да |
| Собственные часы и начисления | Да | Да |
| Чужие часы, ставки и начисления в отчётах | Нет | Да |
| Создание, изменение, отмена смен | Нет | Да |
| Управление сотрудниками, типами, ставками | Нет | Да |
| Выставление собственной смены, отзыв объявления | Да, по правилам | Да, для любой допустимой смены |
| Забор чужой открытой смены | Да, без согласования | Переназначение через административное действие |
| Блокировка биржи, откат обмена | Нет | Да, с причиной |
| Корректировка часов и денег | Нет | Да, с причиной |
| Собственные уведомления и устройства | Да | Да |
| Рассылка команде, журнал действий | Нет | Да |

Сервер проверяет активность пользователя, роль и принадлежность объекта на каждом запросе, включая подписки и deep links. Клиент не передаёт доверенную роль. Публичной саморегистрации нет: сотрудников создаёт админ, первоначального админа — установочная серверная команда без общего пароля в коде.

Список команды для графика содержит только id и отображаемое имя. Телефоны, индивидуальные ставки, финансовые комментарии и детализация часов не попадают в общий API или общий realtime-канал. Длительность конкретной смены можно вычислить из видимого времени; скрыть её математически невозможно. Ограничение относится к приватным итогам и финансовым данным.

Вход: нормализованный телефон и пароль; PIN можно добавить как отдельный ограниченный способ входа с защитой от перебора. Пароль хранится как Argon2id-хеш. Сессия — защищённая HttpOnly-cookie, HTTPS, CSRF-защита для изменений, ограничение попыток входа. Деактивация немедленно отзывает сессии и realtime-доступ.

## 4. Пользовательские сценарии

1. Админ создаёт сотрудника и выдаёт временный пароль с обязательной сменой. Бариста входит и сразу видит свой ближайший выход.
2. Админ выбирает день, сотрудника и тип. Сервер подставляет значения типа, проверяет время и пересечения, фиксирует ставку, сохраняет смену и уведомление. Подключённые клиенты обновляют график.
3. Бариста открывает будущую собственную смену и нажимает «Выставить на биржу». Подтверждение объясняет: пока смену не забрали, ответственность остаётся за ним.
4. Другой бариста видит время, длительность и расчёт оплаты именно для себя. Нажимает «Забрать смену», подтверждает действие. Сервер атомарно меняет назначение без согласования админом.
5. При конфликте двух запросов один получает успех, второй — «Эту смену уже забрали». Повтор из-за сетевого сбоя не создаёт второй обмен.
6. Админ откатывает ошибочный обмен, указывая причину. Сервер проверяет активность прежнего сотрудника и отсутствие пересечений; при конфликте предлагает отдельное переназначение.
7. После окончания смены сервер отмечает её отработанной. Бариста видит начисление за день. Корректировка администратора отображается отдельной строкой с причиной.
8. Без интернета пользователь видит сохранённый график и время последней синхронизации. Передача смен и другие изменения требуют подключения; после восстановления данные перечитываются.

## 5. График и календарь

Сервер принимает дату смены и локальные часы в Europe/Minsk, преобразует их в абсолютные `timestamptz`. Не принимает клиентские `hours`, `amount`, `deadline` или `timezone` как источник истины. Бизнес-проверки используют часы БД; временная зона ОС телефона не влияет на результат.

Правила сохранения:

- Реальные дата и часы с точностью до минуты, `start < end`.
- Минские даты начала и конца равны дате смены. Интервал 22:00–02:00 отклоняется: «Ночные смены не поддерживаются. Начало и окончание должны быть в одном дне».
- У одного сотрудника нет пересекающихся неотменённых смен. Интервалы полуоткрытые `[start, end)`: 09:00–12:00 и 12:00–15:00 допустимы.
- Админ может сохранить смену без сотрудника: это «Не назначена». Она видна как свободное назначение, но в MVP не становится объявлением бариста автоматически.
- Отменённая смена не участвует в начислениях и проверке занятости. Смена с историей не удаляется физически: действие «Удалить» отменяет её с причиной.
- Месячный вид показывает полные недели, включая подписанные граничные даты соседних месяцев со светлым фоном. На телефоне семь колонок помещаются без горизонтальной прокрутки; нажатие даты открывает день. Кнопка и API повторения недели удалены.
- Изменение назначения, времени, статуса, ставки или типа закрывает открытое объявление в той же транзакции. Требуется открыть его заново после изменения.
- Закрытая смена защищена от обычного редактирования; исправления проходят через отдельное действие с причиной и пересчётом.

Статусы жизненного цикла: `planned → confirmed → worked → closed`; допустима отмена `cancelled` с причиной. `confirmed` выставляет админ. `worked` автоматически выставляется после окончания, если смена не отменена; это расчёт по расписанию, а не доказательство присутствия. Реального учёта входа/выхода в MVP нет.

«Открыта на бирже», «Занята», «Обменена» — отображаемые признаки биржи и истории, отдельные от жизненного цикла. Смена может быть одновременно подтверждена и выставлена на биржу. Успешная передача сохраняет запись истории и флаг `has_been_exchanged`, исключающий повторное выставление. API возвращает жизненный статус и признаки отдельно.

Периоды запросов задаются реальными датами с исключённой правой границей. День и границы месяца вычисляются по Минску. Неделя начинается с понедельника, в том числе при пересечении года. Календарь корректно обрабатывает февраль високосного года.

## 6. Типы смен и ставки

Тип содержит название, часы по умолчанию, вычисляемую длительность, `hourly`/`shift`, фиксированную оплату при модели `shift`, активность, разрешение биржи и семантическую метку палитры. Почасовая ставка задаётся сотруднику и в форме типа отсутствует. Примеры: открытие, закрытие, полная, короткая, подмена, обучение, праздничная.

При создании админ выбирает дату и добавляет до 50 назначений: сотрудник и тип смены для каждого. Часы берутся из типа, оплата — из действующих правил сотрудника; ручные поля начала и окончания в новой форме отсутствуют. Группа сохраняется целиком или откатывается целиком с понятной ошибкой конфликта. Ручное изменение часов и оплаты доступно в редакторе существующей смены. Комментарий, статус и блокировка биржи общие для группы. Неактивный тип нельзя выбрать для новой смены; история сохраняется. Изменение стандартных часов или ставки типа не переписывает существующие смены.

Разрешение биржи проверяется по текущему типу: отключение закрывает его открытые объявления транзакционно. Конкретную смену можно заблокировать отдельно с причиной.

Порядок определения оплаты: явное переопределение админом в смене → индивидуальная ставка сотрудника → фиксированная оплата типа при модели shift. Тип «По ставке сотрудника» использует сумму и модель оплаты из профиля: hourly — за час, shift — за всю смену. Поэтому сотруднику с фиксированной индивидуальной оплатой можно назначить этот тип и передать его через биржу без пересчёта фиксированной суммы в почасовую. Фиксированный тип использует ставку shift сотрудника или сумму типа. Ручная ставка использует модель выбранного типа. Итоговые модель и ставка фиксируются в снимке оплаты назначения.

При заборе ставка пересчитывается для нового сотрудника; явное переопределение смены сохраняется. До подтверждения получатель видит свой серверный расчёт. Предпросмотр содержит версии смены, типа и индивидуальной ставки; если они изменились, сервер возвращает `409 QUOTE_CHANGED` и новый расчёт для повторного подтверждения. Прежний снимок хранится в истории обмена, чужая ставка новому сотруднику не раскрывается.

## 7. Подсчёт часов

`duration_minutes = (end_at - start_at) / 60 секунд`.
`base_hours = duration_minutes / 60`.
`effective_minutes = duration_minutes + сумма корректировок минут`.

Обед и любые перерывы не вычитаются. В базе длительность хранится в целых минутах, без накопления погрешности дробных часов. В интерфейсе можно показывать «8 ч 45 мин» и «8,75 ч».

| Интервал | Минуты | Часы |
| --- | --- | --- |
| 09:00–18:00 | 540 | 9 |
| 10:00–16:00 | 360 | 6 |
| 08:30–17:15 | 525 | 8,75 |

План — будущие/текущие неотменённые назначения. Отработано — смены `worked`/`closed`. Прогноз и начислено отображаются раздельно; полная стоимость текущей смены не называется заработанной до её окончания.

Корректировка относится к конкретной смене и неизменному получателю, содержит целое изменение минут, денежный результат, автора и обязательную причину. Итоговые минуты не могут быть отрицательными. Доплаты к будущим сменам разрешены, но наличие корректировок запрещает передачу владельца в редакторе, на бирже и при откате. Старые ошибочно перенесённые корректировки учитываются исходному сотруднику; неизвестная старая ставка требует проверки админом.

## 8. Расчёт BYN за день

Почасовая оплата: `base_amount = round(effective_minutes × rate_byn / 60, 2)`.
Фиксированная: `base_amount = rate_byn`; изменение часов само по себе её не меняет.
Итог смены: `base_amount + денежные корректировки`.
Итог дня: сумма округлённых сумм неотменённых отработанных смен за минскую дату. Неделя/месяц суммируют дневные суммы, а не пересчитываются из округлённых часов.

Деньги — `numeric`, десятичная арифметика на сервере, округление до копейки по правилу half-up. JSON передаёт деньги строками (`"108.00"`), UI форматирует `108,00 Br`. Индивидуальная и ручная почасовая ставки должны быть больше нуля. Для фиксированной оплаты типа и ручной фиксированной суммы допустим ноль. Пустые корректировки (0 минут и 0 Br) не сохраняются; старые пустые записи не блокируют передачу. Если корректировка приводит к отрицательной сумме смены, MVP отклоняет её.

Примеры: 540 мин × 12 Br/ч = 108,00 Br; 525 мин × 12 Br/ч = 105,00 Br; фиксированная смена 85 Br = 85,00 Br независимо от длительности. При почасовой модели корректировка +30 мин и +5 Br для первой смены даёт 119,00 Br.

`payroll_daily` — пересчитываемая проекция смен и корректировок, не второй независимый источник сумм. Смена владельца до начала переносит будущую оплату новому сотруднику. Уже сохранённые суммы прошлого не меняются при редактировании справочника ставок. Приватные запросы разрешены владельцу и админу, чужой id не обходит проверку.

## 9. Биржа смен: забор с 10:00 до 19:00

Эффективное закрытие учитывает последнее рабочее окно биржи перед сменой. Для начала до 10:00 включительно это 19:00 предыдущего дня по Минску; для начала после 10:00 и до 19:00 — начало смены; для начала в 19:00 и позже — 19:00 дня смены. Этот срок используется в карточке, в базе и в серверных проверках публикации, просмотра условий и передачи.
Разрешено только если серверное время строго меньше срока. Ровно в момент закрытия — уже нельзя. На будущие дни выставление разрешено заранее до этого срока.

Дополнительно забирать смену можно только с 10:00 включительно до 19:00 исключительно текущего дня по Europe/Minsk. Это действует и для завтрашних назначений. Просмотр объявления и расчёта доступен вне этого интервала, кнопка подтверждения отключена; сервер также отклоняет запрос с EXCHANGE_HOURS. Публикация и отзыв не ограничиваются часом 10:00.

Примеры:

- Смена завтра в 09:00: срок объявления — сегодня в 19:00; после этой границы выставить или забрать её нельзя.
- Смена сегодня в 20:00: в 18:59:59 можно, в 19:00:00 нельзя.
- Смена сегодня в 09:00: после 09:00 нельзя, даже если 19:00 ещё не наступило.
- Смена завтра: в 09:59:59 сегодня забрать нельзя, в 10:00:00 можно, в 19:00:00 уже нельзя.

При выставлении сервер проверяет владельца, активность, отсутствие отмены/закрытия, отсутствие предыдущей успешной передачи, блокировок админа и запрета типа. У смены максимум одно открытое объявление. Исходный сотрудник остаётся ответственным, пока другой не забрал смену. Истечение объявления не снимает назначение.

Забирающий — активный бариста, не текущий владелец. Объявление открыто, смена не началась, дедлайн не наступил, у получателя нет пересечений. Никакого ожидания подтверждения админа.

Атомарный забор:

1. Начать транзакцию, проверить сессию и ключ идемпотентности.
2. Заблокировать строку смены, затем её объявление через `SELECT … FOR UPDATE`; все операции над ними используют тот же порядок блокировок.
3. После ожидания блокировки получить актуальное время БД (`clock_timestamp()`), заново проверить статус, владельца, границы, активность, разрешение типа и версии предпросмотра. Не использовать время начала долго ожидавшей транзакции как текущее.
4. Назначить получателя и снимок его оплаты. Ограничение БД запрещает пересечение даже при одновременном заборе разных объявлений одним сотрудником.
5. Пометить объявление `taken`, поставить `has_been_exchanged`, сохранить историю, аудит, уведомления и события в outbox в этой же транзакции.
6. Зафиксировать транзакцию. Только после фиксации доставлять события и push.

Второй запрос к уже забранному объявлению: `409 EXCHANGE_ALREADY_TAKEN`, «Эту смену уже забрали». Точный повтор успешного запроса с тем же ключом идемпотентности возвращает исходный результат без повторного эффекта.

Отзыв собственного объявления допустим до эффективной границы. Фоновая задача закрывает просроченные объявления как `expired`; каждый запрос всё равно самостоятельно проверяет время, поэтому задержка задачи не оставляет биржу открытой.

Откат — отдельная транзакция админа с обязательной причиной. До начала смены проверяет прежнего сотрудника и его занятость, восстанавливает исходное назначение и снимок оплаты, выставляет `rolled_back`, но не открывает объявление заново. Флаг предыдущего обмена сохраняется. Для начавшейся/прошедшей смены админ использует отдельное исправление назначения/начислений с аудитом. Админ также не может создать пересечение или ночную смену.

Ошибка пересечения возвращает понятный интервал конфликта без чужих финансов. Открытая карточка не резервирует смену: итог всегда решает сервер.

## 10. Push и центр уведомлений

Каждое событие сначала сохраняет персональную запись `notifications` и задание доставки в outbox. Рабочий процесс отправляет push после фиксации транзакции; сбой FCM не откатывает назначение смены. Повторная доставка использует уникальный ключ события и получателя, не создавая повторов в истории. Недействительные токены отключаются, временные ошибки повторяются с увеличением интервала.

| Событие | Получатели |
| --- | --- |
| Назначение, изменение, отмена смены | Затронутый сотрудник |
| Напоминание за 2 часа / 1 час | Владелец, если выбран соответствующий интервал |
| Выставление на биржу | Активная команда по настройкам, исключая автора и владельца; без повторной рассылки той же смены |
| Забор смены | Прежний и новый владельцы, админы |
| Скорое закрытие биржи | Владелец открытого объявления |
| Истечение объявления | Владелец и админы |
| Откат или ручная корректировка | Затронутые сотрудники и админы |
| Изменение команды и типов смен | Только журнал действий, без уведомлений |
| Изменение личной ставки | Только сотрудник, чья ставка изменилась |
| Свободное назначение к началу смены | Админы |

Напоминание о бирже — за 30 минут до эффективного закрытия; текст указывает фактическую причину: начало смены или 19:00. Уже просроченные напоминания не отправляются. Если объявление создано менее чем за 30 минут до границы, условие показывается сразу в карточке.

Задачи напоминаний привязаны к версии смены и владельцу. После изменения/передачи устаревшие задачи отменяются; перед отправкой worker ещё раз проверяет актуальность и серверное время. После простоя не рассылаются напоминания к уже начавшейся смене.

Категории настроек: изменения графика, биржа, напоминания 2 ч/1 ч, корректировки, сообщения администратора. Отключение push не удаляет историю в центре уведомлений. Финансовые детали в push на экране блокировки по умолчанию не отправляются.

Deep links используют внутренние маршруты `/shifts/:id`, `/exchange/:id`, `/me/payroll`, `/notifications`; при открытии сервер заново проверяет доступ. Пользователь может иметь несколько устройств — токены хранятся отдельно от `users`.

FCM Web требует HTTPS, разрешения пользователя и service worker. Поддержка проверяется на целевых браузерах и установленных PWA; отказ в разрешении объясняется в настройках, центр уведомлений продолжает работать. До выбора окончательной клиентской платформы требуется проверка push на реальных Android и iPhone. Источник: [FCM Web — запуск](https://firebase.google.com/docs/cloud-messaging/web/get-started), [приём сообщений](https://firebase.google.com/docs/cloud-messaging/web/receive-messages).

## 11. Realtime, синхронизация и отсутствие сети

После фиксации транзакции outbox публикует `schedule.changed`, `exchange.changed`, `payroll.changed`, `notification.created`. WebSocket передаёт идентификаторы, версии и область изменений. Общий канал содержит только публичные поля графика. Личные финансы и уведомления идут в персональный канал, административный журнал — только админу.

Каждое событие имеет `event_id`, `entity_id`, `version`, `occurred_at`. Клиент дедуплицирует события и перечитывает разрешённые API-запросы. Последовательность доставки не считается гарантированной: версия не позволяет старому ответу затереть новый. После переподключения выполняется полное обновление видимого периода, биржи, личных итогов и уведомлений. Если курсор событий недоступен, клиент также делает полный refetch.

Цель приёмки: у подключённых клиентов график и биржа обновляются не позднее 2 секунд после фиксации в тестовой среде при согласованной нагрузке в 20 одновременных пользователей. Это целевой показатель, который нужно измерить, а не обещание доставки push по времени.

Кэш PWA: оболочка приложения и последние разрешённые данные пользователя. Приватный API не попадает в общий service-worker cache. IndexedDB отделена по пользователям и очищается при выходе/смене аккаунта; предыдущий пользователь не виден следующему. Статус «Нет подключения», дата последней синхронизации и устаревшие значения показаны явно.

Изменения и забор смен офлайн не ставятся в очередь. При возвращении сети серверное время и данные обновляются прежде, чем снова доступны действия. Смещение клиентских часов можно использовать для приблизительного обратного отсчёта на базе `server_now` и монотонного таймера, но любое действие заново решает сервер.

## 12. Структура базы данных

Общие правила: UUID-ключи, `created_at`/`updated_at` как `timestamptz`, деньги `numeric(12,2)`, времена смен с минутной точностью, внешний ключ без каскадного удаления истории. `version` увеличивается при изменениях. Пароли, токены и телефоны не попадают в аудит значений или realtime-события.

| Таблица | Основные поля и назначение |
| --- | --- |
| `users` | id, name, phone (unique), role, status, password_hash, must_change_password, version, timestamps |
| `sessions` | id, user_id, token_hash, expires_at, revoked_at; серверные сессии |
| `employee_rates` | id, user_id, pay_type, rate_byn, version, changed_by; текущая индивидуальная ставка, история в аудите |
| `shift_types` | id, name, default_start_time, default_end_time, pay_type, default_rate_byn, allow_exchange, is_active, color_label, version, created_by |
| `shifts` | id, date, start_at, end_at, timezone, shift_type_id, user_id nullable, lifecycle_status, duration_minutes, pay_type_snapshot, rate_byn_snapshot, rate_source, has_rate_override, exchange_locked, exchange_lock_reason, has_been_exchanged, version, comment, created_by, updated_by |
| `exchange_listings` | id, shift_id, listed_by_user_id, status, taken_by_user_id, deadline_at, closes_at, taken_at, timestamps |
| `exchange_transfers` | id, listing_id unique, from_user_id, to_user_id, old_pay_snapshot, new_pay_snapshot, taken_at, rolled_back_at, rolled_back_by, rollback_reason |
| `payroll_adjustments` | id, shift_id, user_id, minutes_delta, amount_delta_byn, reason, created_by, reversed_adjustment_id, created_at |
| `payroll_daily` | user_id + date (unique), worked_minutes, base_amount_byn, adjustment_amount_byn, total_byn, calculation_version, updated_at |
| `notification_preferences` | user_id + category (unique), push_enabled, reminder_minutes |
| `push_devices` | id, user_id, token (unique), platform, last_seen_at, revoked_at |
| `notifications` | id, user_id, event_id, type, title, body, deep_link, read_at, created_at |
| `notification_deliveries` | notification_id, device_id, status, attempts, sent_at, last_error; отдельно для каждого устройства |

| `scheduled_jobs` | id, shift_id, shift_version, recipient_id, kind, run_at, status, dedup_key |
| `idempotency_keys` | user_id + route + key (unique), request_hash, response, status, expires_at |
| `settings` | key, value, updated_by, updated_at; часовой пояс фиксирован, не редактируется клиентом |

`hours`, `amount_byn`, `is_on_exchange` и `exchange_deadline` в API могут быть вычисляемыми полями. Их не следует поддерживать как независимые редактируемые копии одних данных. Оплата назначения хранится в снимке; рассчитанные итоги — в проекции. Для MVP отметки официальной выплаты и бухгалтерские документы не нужны.

Обязательные ограничения и индексы:

- `CHECK (start_at < end_at)` и проверка обеих минских дат на равенство `date`; `timezone = 'Europe/Minsk'`.
- GiST exclusion с `btree_gist`: `(user_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&)` для назначенных неотменённых смен. Это защищает от пересечений независимо от гонки запросов.
- Частичный уникальный индекс `exchange_listings(shift_id) WHERE status = 'open'`.
- Неотрицательные ставки, ограничения enum-статусов, уникальные phone и ключи дедупликации.
- Индексы `shifts(date)`, `shifts(user_id, date)`, `exchange_listings(status, closes_at)`, `notifications(user_id, created_at)`, `audit_logs(created_at)`, `outbox_events(processed_at, available_at)`.
- Аудит и корректировки дописываются; исправление корректировки — новая компенсирующая запись, а не затирание старой.

Проверка периода выполняется ограничением БД, а атомарная передача — транзакцией с блокировками строк. Возможности подтверждены официальной документацией: [PostgreSQL range constraints](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT), [SELECT и блокировки](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE).

## 13. Основные API

База `/api/v1`. Все изменяющие методы требуют сессии и CSRF-защиты; административные дополнительно проверяют роль на сервере. На изменения смены передаётся ожидаемая версия (`If-Match`); конфликт даёт `409 STALE_VERSION`. Для бизнес-действий нужен `Idempotency-Key`.

| Метод и маршрут | Доступ | Результат |
| --- | --- | --- |
| `POST /auth/login` | Без сессии, rate limit | Вход по телефону/паролю |
| `GET /auth/me` | Активный пользователь | Собственный профиль, роль, server_now |
| `POST /auth/logout` | Сессия | Отзыв сессии и закрытие подписки |
| `POST /auth/change-password` | Владелец | Смена временного/текущего пароля |
| `GET /time` | Активный пользователь | server_now и Europe/Minsk |
| `GET /team` | Все | Только id и имя активных сотрудников |
| `GET, POST /employees` | Админ | Полный список / создание |
| `PATCH /employees/:id` | Админ | Имя, статус, телефон, ставка; причина для значимых изменений |
| `POST /employees/:id/deactivate` | Админ | Отзыв доступа; обработка будущих смен |
| `GET /schedule?from=&to=` | Все | Общий график без денег и личных комментариев |
| `GET /me/shifts?from=&to=` | Владелец | Свои смены с личной оплатой |
| `GET /shifts/:id` | Все с фильтрацией полей | Общая карточка; финансы только владельцу/админу |
| `POST /shifts` | Админ | Создать смену |
| `PATCH /shifts/:id` | Админ | Изменить смену с проверкой версии |
| `DELETE /shifts/:id` | Админ, причина | Отменить без потери истории |
| `POST /shifts/:id/status` | Админ | Допустимый переход статуса |
| `POST /shifts/:id/copy` | Админ | Копирование на другую дату |
| `PATCH /me/name` | Владелец | Изменение имени и фамилии с проверкой версии |
| `POST /shifts/batch` | Админ, Idempotency-Key | До 50 назначений по типам одной транзакцией |
| `GET, POST /shift-types` | Админ | Список / создание типов |
| `PATCH /shift-types/:id` | Админ | Изменение или деактивация типа |

| `POST /shifts/:id/exchange` | Владелец / админ | Выставление допустимой смены |
| `POST /exchange/:id/withdraw` | Автор / админ | Отзыв объявления |
| `GET /exchange/:id/quote` | Бариста | Собственная будущая оплата и версии расчёта |
| `POST /exchange/:id/take` | Бариста | Атомарный забор, без согласования |
| `POST /exchange/:id/rollback` | Админ, причина | Откат передачи |
| `POST /shifts/:id/exchange-lock` | Админ, причина | Блокировка / разблокировка биржи |
| `GET /me/payroll?from=&to=` | Владелец | Дневные часы и суммы, план отдельно |
| `GET /payroll?user_id=&from=&to=` | Админ | Сотрудник или вся команда |
| `POST /shifts/:id/adjustments` | Админ, причина | Корректировка минут/денег |
| `GET /notifications` | Владелец | Персональная история |
| `PATCH /notifications/:id/read` | Владелец | Отметка прочтения |
| `PUT, DELETE /me/push-devices/:id` | Владелец | Регистрация / отзыв своего устройства |
| `GET, PATCH /me/notification-preferences` | Владелец | Настройки категорий |
| `POST /admin/notifications` | Админ | Отправка сотруднику/команде |
| `GET /audit-logs` | Админ | Фильтруемый журнал с пагинацией |
| `DELETE /audit-logs` | Админ | Удаление записей по `through` включительно (день по Минску) с обязательной причиной; сегодняшняя или прошедшая дата. В транзакции создаётся новая запись о том, кто очистил журнал, с датой границы и количеством удалённых записей. Смены, сотрудники и начисления не удаляются. |
| `GET, PATCH /settings` | Админ | Разрешённые настройки |

Деактивация: сервер возвращает будущие назначения на проверку. Админ явно выбирает переназначение или перевод в свободные, причина обязательна. Изменение активности, закрытие объявлений, обработка назначений, отзыв сессий и аудит проходят атомарно. Последнего активного админа деактивировать нельзя.

Общий формат ошибки: `{ "code": "SHIFT_STARTED", "message": "Смена уже началась", "request_id": "…" }`. Основные статусы: `401` нет действующей сессии, `403` недостаточно прав, `404` объект не существует или скрыт владельческой проверкой, `409` конфликт, `422` неверные значения, `429` превышение частоты. Бизнес-коды: `EXCHANGE_DEADLINE_PASSED`, `SHIFT_STARTED`, `SHIFT_OVERLAP`, `EXCHANGE_ALREADY_TAKEN`, `EXCHANGE_FORBIDDEN`, `QUOTE_CHANGED`, `STALE_VERSION`.

Списки ограничены по периоду и пагинации. Доступ проверяется до сериализации. Пароли/сессионные токены не пишутся в журналы. Серверный ключ FCM и доступ к БД никогда не включаются в клиентскую сборку.

## 14. UI/UX в красно-бело-чёрной теме

| Токен | Значение | Применение |
| --- | --- | --- |
| accent | `#E10600` | Главное действие, активная навигация, биржа |
| background | `#FFFFFF` | Фон страницы |
| text | `#111111` | Основной текст |
| surface-dark | `#1A1A1A` | Сводка и подтверждённые статусы |
| surface | `#F6F6F6` | Карточки и второстепенные области |
| text-secondary | `#666666` | Мелкий вспомогательный текст |
| border | `#CCCCCC` | Разделители и неактивные элементы |

Красный не используется для каждого числа. На экране одно доминирующее действие. Статусы всегда подписаны, цвет лишь помогает распознаванию. Для мелкого текста на белом выбран более контрастный `#666666`; контраст конкретных сочетаний проверяется при реализации.

Мобильная карточка: дата и статус сверху, крупно 09:00–18:00, ниже «Открытие · 9 ч», затем «Ожидаемая оплата 108,00 Br» только владельцу. Кнопка «Выставить на биржу» показывает доступность и причину блокировки. На бирже действие «Забрать смену» раскрывает собственный расчёт до подтверждения.

Главная бариста: ближайшая смена сверху, затем сегодня/завтра, часы и начисления периода, ссылка на открытую биржу. Если смены нет — «Сегодня выходной» и следующая дата. Если график пуст — ясное пустое состояние без вымышленных смен.

Админ: постоянная боковая навигация, неделя по сотрудникам, заметные свободные назначения, панель смены справа. Видны текстовые часы и статусы; выбор времени доступен клавиатурой. Перетаскивание можно добавить позже, все действия уже доступны обычной формой.

Размеры: основной текст от 16 px, области нажатия от 44×44 px, заметный фокус, подписи полей, сообщения рядом с ошибочным значением. Диалоги удерживают фокус и возвращают его на вызвавшую кнопку. На узких экранах панель смены становится полноэкранной, таблица имеет понятную прокрутку и альтернативный список дня.

Состояния каждого запроса: загрузка, результат, пусто, ошибка с повтором, отсутствие сети. У кнопки забора после нажатия появляется прогресс; финальный успех показывается только после ответа сервера. Устаревшее объявление исчезает с сообщением, почему действие не удалось. Причина обязательна при откате/корректировке; её нельзя заменить заранее заполненным бессодержательным текстом.

| 4. Мобильная часть и расчёты | Главная, мои смены, часы, дневные BYN, план/факт, корректировки | Формулы и приватность подтверждены интеграционными проверками |
| 5. Биржа | Выставление, отзыв, предпросмотр оплаты, атомарный забор, откат, журнал | Конкурентные запросы и границы начала/19:00 проходят проверки |
| 6. Синхронизация и push | Outbox, WebSocket, FCM, история, настройки, worker напоминаний | Изменения видны на двух устройствах, уведомления проверены на Android/iPhone |
| 7. PWA и пилот | Установка, чтение кэша, reconnect, адаптивность и массовое назначение | Выполнены критерии ниже; резервная копия восстановлена в тестовой среде |

Все пункты входят в целевую первую версию, но разрабатываются последовательно. Обещать готовность MVP после одного только интерфейса нельзя: этапы биржи, прав, push и синхронизации обязательны.

Проверки: модульные для денежных правил и календаря; интеграционные на настоящей PostgreSQL для прав, транзакций и пересечений; Playwright для ключевых сценариев админа/бариста; реальные устройства для push и PWA. Заглушка FCM подходит для CI, но не заменяет проверку доставки на устройстве.

## Предлагаемый технический стек

Рекомендация для MVP: единый TypeScript-монорепозиторий с React PWA и отдельным NestJS API. Для одной кофейни это позволяет разделить права, переиспользовать интерфейсные компоненты и держать правила биржи в одной серверной реализации.

| Слой | Выбор | Назначение |
| --- | --- | --- |
| Бариста и админ | React + TypeScript + Vite, React Router | Две зоны интерфейса в одном адаптивном веб-приложении |
| Состояние и формы | TanStack Query, React Hook Form, Zod | Запросы, обновление кэша, формы и валидация |
| Оформление | CSS variables и CSS Modules | Явные токены красно-бело-чёрной темы |
| PWA | Manifest, service worker, Workbox, IndexedDB | Установка и чтение разрешённого кэша |
| API | Node.js поддерживаемой LTS-линейки + NestJS | Серверные модули Auth, Team, Schedule, Payroll, Exchange, Notifications, Audit |
| БД | Поддерживаемая стабильная PostgreSQL, SQL-миграции, `pg` | Транзакции, decimal, ограничения и индексы |
| Realtime | NestJS WebSocket gateway + Socket.IO | Подписки и персональные события после commit |
| Фоновые задачи | Отдельный Node worker + PostgreSQL outbox/jobs | Доставка, дедупликация, напоминания, истечение объявлений |
| Push | Firebase Cloud Messaging Web | Телефонные push с проверкой поддержки и service worker |
| Авторизация | Телефон + пароль, Argon2id, серверные сессии | Полный контроль над ролью, блокировкой и отзывом доступа |
| Проверки | Vitest, интеграционные проверки PostgreSQL, Playwright | Правила, конкурентность, API и пользовательские сценарии |
| Развёртывание | Docker Compose локально; HTTPS reverse proxy, API + worker + PostgreSQL в окружении пилота | Воспроизводимый запуск, секреты вне репозитория, резервное копирование |

PostgreSQL выбран в том числе из-за встроенных диапазонов и исключающих ограничений, подходящих для запрета пересечений. WebSocket gateway описан в [документации NestJS](https://docs.nestjs.com/websockets/gateways). Условия FCM Web проверяются по [официальному руководству](https://firebase.google.com/docs/cloud-messaging/web/get-started).

Конкретные совместимые версии закрепляются lockfile при начале реализации и проверяются сборкой/CI. Redis и отдельный брокер для одной кофейни на старте не обязательны. При нескольких экземплярах API понадобится общий механизм распространения событий; outbox остаётся надёжным источником событий.

Решения, принятые для устранения неоднозначностей ТЗ: будущее объявление разрешено заранее; биржа закрывается также при начале смены; исходный владелец отвечает за незабранную смену; повторная передача через биржу запрещена; после отката объявление не открывается автоматически; факт считается по завершённому расписанию; при передаче индивидуальная ставка принадлежит получателю. Эти правила должны быть видны в интерфейсе и сохранены в серверных проверках.
